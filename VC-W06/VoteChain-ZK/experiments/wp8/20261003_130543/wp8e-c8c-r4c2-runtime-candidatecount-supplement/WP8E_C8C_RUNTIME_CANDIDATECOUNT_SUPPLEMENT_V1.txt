WP8E C8C RUNTIME candidateCount BENCHMARK SUPPLEMENT V1
=======================================================

CLASSIFICATION
--------------

This document is a PRE-EXECUTION benchmark supplement.

It does not modify or retrospectively rewrite Final Benchmark Protocol V2.

It freezes mechanics that were still unspecified for the already-registered
runtime candidateCount={2,4,8,16} final benchmark dimension.

No active Solidity, circuit, R1CS, WASM, proving key, verification key,
verifier, or cryptographic architecture changes.


1. EXPERIMENTAL QUESTION
------------------------

Measure accepted-vote transaction gas and local cast-to-receipt latency under:

candidateCount = {2,4,8,16}

inside the single frozen active K16 DIRECT deployment.

This is distinct from WP8D compile-time K-profile circuit/proving scaling.


2. ACTIVE TOPOLOGY
------------------

MAX_CANDIDATES = 16

MERKLE_DEPTH = 17

Groth16 public signals = 73

ciphertext slots = 16

tally slots = 16

The active castVote path retains fixed MAX=16 representation/work.

Therefore candidateCount must not be described as shortening the active
Solidity vote loop.

same depth-17 Merkle membership path

same eligible root

same electionId

same contractDomain

same election public key Y

same 16 randomness values

Thus selected slot 0 is active at all four levels.

Only the following public proof-bound configuration values vary:

candidateCount

candidateManifestHash

electionContextHash


7. EXPECTED CONTROLLED CONSEQUENCES
-----------------------------------

Because secret and electionId are held fixed, the expected nullifier is held
constant across levels.

Because bit vector, randomness and election public key are held fixed, the
expected 16-slot ciphertext is held constant across levels.

These expectations must be validated during input/proof construction before
any benchmark execution.

9. PILOT POLICY
---------------

Before the final campaign, execute one accepted-vote pilot for each runtime
level using the final frozen runner.

Pilot observations are NONFINAL and excluded from final statistics.

If any pilot fails, stop and preserve evidence before a final campaign.


10. FINAL REPETITION PLAN
-------------------------

Per runtime level:

5 warm-up observations

20 measured observations

Across four levels:

20 warm-up observations

80 measured observations

100 total final accepted-vote observations

Each observation uses a completely fresh Anvil chain.

No successful observation is reused between levels.


11. BALANCED EXECUTION ORDER
----------------------------

Base order:

2,4,8,16

Round r rotates the base order by:

(r - 1) mod 4

The frozen execution matrix is stored separately.

Across the 20 measured rounds, every runtime level occupies each execution
order position exactly five times.


12. PER-OBSERVATION PROCEDURE
-----------------------------

For every observation:

1. start fresh Anvil;

2. deploy the frozen verifier;

3. deploy the frozen VoteChainDirect contract;

4. configure the level-specific election;

5. activate the election;

6. submit exactly one accepted vote;

7. preserve receipt;

8. perform correctness checks;

9. stop Anvil.

Deployment/configuration/activation are preparation operations and not the
accepted-vote measurement itself.


13. TIMING INTERVAL
-------------------

The latency timer starts immediately before the local:

cast send

operation and ends immediately after that command returns with receipt output.

Included:

local cast process startup

JSON-RPC interaction

instant local Anvil mining

receipt return

Excluded:

Anvil startup

contract deployment

election configuration

activation

proof generation

fixture construction

post-return receipt parsing

post-receipt state reads

tally validation

This metric is local process/RPC + instant Anvil mining latency.

It is not public-network confirmation latency and not end-to-end biometric
voting latency.

18. INTERPRETATION GUARDRAIL
----------------------------

Observed gas differences across levels must not be described as isolated
candidateCount opcode/loop cost.

The active castVote path retains fixed MAX=16 processing, while each level
uses a distinct proof and distinct proof-bound public values.

Groth16 proof coordinate and calldata byte composition may therefore
contribute to measured transaction-gas differences.

The proper result is:

accepted-vote transaction sensitivity of the frozen active K16 system under
four runtime candidateCount configurations.

--------------
